1.Why this exists

The current product (dripclientofficial.dev) is a Next.js 16 + Prisma + MongoDB digital-key storefront, running on a VPS with PM2 + nginx. This is too expensive/complex for resale customers, most of whom only have:

  • Shared PHP hosting (cPanel, MySQL, no shell/SSH, no Node runtime)
  • Little to no DevOps knowledge — needs to be "upload via FTP/File Manager and go"

Goal

Reimplement the same product surface in plain PHP + MySQL, deployable by uploading files and importing one SQL file — no Composer, no build step, no Node.

Non-goal: this is not a literal transpile of the Next.js code. It's a from-scratch PHP implementation that reproduces the same behavior and features, using PHP-idiomatic patterns (server-rendered pages + PDO + sessions).

3.Full feature scope nothing dropped

Organized by module, mapped 1:1 to the current Prisma models/routes.

3.1 Storefront (public)

  • Home: categories, product grid, bestseller/new/pinned sorting, banners, flash-sale banner, promo banner
  • Product detail: durations × versions, price table (user/reseller/special-price aware), stock indicator, reviews (approved only), demo URL
  • Category browse
  • FAQ page, static pages (CMS pages by slug)
  • Public seller/user profile pages (/[username]) — bio, socials, featured products, profile border, emoji status, premium badge
  • Leaderboard (top sellers/resellers)
  • Developer docs page (Platform API reference, human-readable)

3.2 Auth & account

  • Register / login (email + password), email verification
  • Forgot password via emailed OTP (rate-limited, hashed OTP, expiry, attempt counter)
  • Change email / change password from account settings
  • Google OAuth login (optional; standard OAuth2 authorization-code flow, no SDK needed)
  • 2FA (TOTP) enable/disable + hashed backup codes
  • Avatar upload, bio, social links, public/private profile toggle
  • Username change (Premium-only, 30-day cooldown)
  • Session/device handling — plain PHP session, "remember me" cookie (hashed token in DB)
  • Ban enforcement (banned users blocked at login/session-check with ban reason shown)

3.3 Wallet & payments

  • Wallet balance (integer cents, USD only)
  • Deposit rails: Binance Pay, QRIS, UPI, eSewa, Manual (admin-defined methods with instructions/QR)
  • Deposit lifecycle: PENDING → PROCESSING → COMPLETED/FAILED/EXPIRED/CANCELLED
  • Proof-of-payment upload for manual deposits, admin review (approve/reject with note)
  • Deposit cron/poll: checks provider status, auto-expires stale ones, credits wallet on confirm (idempotent via transaction_id link)
  • Ledger: transactions table — DEPOSIT, PURCHASE, REFUND, REFERRAL_REWARD, ADMIN_ADJUSTMENT, PREMIUM_PURCHASE, API_FEE, GIFT_CODE
  • Gift codes: admin-generated wallet credit codes, optional user-assignment, redeem flow, kill-switch
  • Cashfree + Binance + manual webhook endpoints

3.4 Catalog & inventory

  • Categories (CRUD, sort order)
  • Products (title, description, images, features list, bestseller/new/pinned/active flags, category)
  • Durations per product (label, days, version grouping, api_code SKU, supplier linkage fields)
  • Duration prices: user price, reseller price, buy/cost price (admin-only), per-currency
  • Keys: inventory per duration (AVAILABLE/SOLD/DISABLED), manual bulk upload and optional supplier auto-generation
  • Per-user special price overrides + audit history
  • Product reviews: star rating, body, verified-buyer flag, PENDING→APPROVED/DISABLED moderation

3.5 Checkout & orders

  • Cart-less direct buy (buy 1 duration at a time) with quantity
  • Promo codes: global/product/duration scope, percent/flat discount, audience targeting, redemption caps, active window, storefront banner
  • Flash sales: same scoping model, percent-only, banner with countdown
  • Guest checkout by email as well as logged-in wallet checkout
  • Order states: PENDING → PAID → FULFILLED / FAILED / REFUNDED
  • Key fulfillment: atomic claim of an AVAILABLE key (row-level lock), mark SOLD
  • Order access token (public order lookup without login)
  • Android ID / device-bound key support

3.6 Reseller / Seller tiering core resale value

  • Roles: USER, SELLER, RESELLER, ADMIN
  • Reseller application flow: submit → PENDING → admin APPROVED/REJECTED
  • Seller permissions granted by admin: can_create_resellers, can_manage_resellers, can_fund_resellers
  • Seller dashboard: create/manage own resellers, fund/cut their wallet, downline leaderboard
  • Reseller-tier pricing at checkout (special price > reseller price > user price)
  • Seller "become a reseller/seller" application pages

3.7 Admin console (full parity)

  • Dashboard/analytics (revenue, orders, signups, top products)
  • Products, Categories, Durations, Prices, Keys (bulk import), Special Prices + history
  • Orders (search/filter/refund/mark fulfilled)
  • Deposits (queue, manual approve/reject, recheck flag, provider raw response viewer)
  • Deposit cron run history
  • Gift codes (create single/batch, assign, kill-switch, claim history)
  • Promo codes, Flash sales, Banners
  • Reviews moderation queue
  • FAQs, Static pages (simple CMS editor)
  • Users (search, ban/unban with reason, role change, wallet adjustment, impersonate)
  • Resellers/Sellers (approve requests, grant permissions, fund management)
  • Support tickets inbox + replies; Issue reports
  • Support bot builder: button-tree editor + keyword-route trainer
  • Broadcasts (pinned announcements by audience)
  • Site config (branding, icons, maintenance mode)
  • Seller/Platform API admin: key issuance, usage stats, developer settlement ledgers
  • Activity/audit logs (auto-purge after 7 days)
  • Supplier API logs viewer
  • Settings: payment gateway keys, manual deposit editor, sandbox toggle

3.8 Notifications & support

  • In-app notification bell
  • Support ticket system: threaded replies, status/priority, freeze-bot flag
  • Persistent support inbox thread per user, unread tracking
  • Support "memory" per user (context-aware bot/admin view)
  • Issue reports: submit-only, tied to key/deposit, admin review queue

3.9 Platform API (developer-facing REST API) kept in scope

  • Seller-issued API keys (LIVE/SANDBOX, prefix + hashed secret, scopes, IP allowlist, rate limit)
  • Endpoints: me, balance, products, pricing, stock, orders, ai-prompt, sdk, openapi.json
  • Idempotency keys for repeated POSTs
  • Per-request usage logging for admin analytics
  • Webhooks: seller-registered URL + signing secret, event list, delivery tracking
  • 1% developer margin fee (API_FEE) auto-applied; daily settlement ledger
  • Sandbox mode toggle (global + per-key)

3.10 Supplier auto-fulfillment kept in scope

  • Optional per-duration link to an upstream supplier catalog product id
  • On stock-out, call supplier API server-to-server to fetch a fresh key
  • Full request/response logging for admin debugging, with fallback flag
  • Manual key upload always remains the primary path — supplier integration is additive

3.11 Support bot / "Little AI" router kept in scope

  • Button-tree bot: Telegram-style step/button flows, one entry step, one fallback step
  • Keyword router: trainable phrase→weight matching, role-gated routes, canned reply + up to 3 buttons
  • No external LLM call required — pure keyword-weight matching in PHP (zero hosting cost)
  • Escalation to a live SupportTicket when a serious route matches or user asks for a human

3.12 Premium membership

  • One-time wallet purchase → lifetime is_premium flag
  • Perks: profile border, username-change ability, referral code page, premium-only purchased-products area
  • Daily settlement ledger for platform revenue share

3.13 Referrals

  • Referral code per user, referred-by linkage
  • Reward transaction on referred user's qualifying action (confirm business rule during build)
  • Referral check endpoint (validate a code before signup)

3.14 Mobile/native shell parity Phase 6

Same approach as the Next.js app: mobile-responsive PHP site wrapped in a minimal Capacitor/WebView shell. No PHP-side work beyond ensuring a good "app-like" mobile experience and a native handoff endpoint.

4.Explicitly out of scope for v1

Nothing was cut per instruction ("sab kuch daalo") — the full list in Section 3 is the target. The only true out-of-scope item is:

UI pixel parity

1:1 UI pixel parity with the Next.js/shadcn design system is not a goal. PHP edition gets its own server-rendered Tailwind UI inspired by the same layout, not a literal component port (React components don't translate to PHP). If pixel-parity is wanted, it becomes its own phase — say so and it'll be added.

5.Data model (MySQL)

Direct translation of the Prisma/Mongo schema to normalized MySQL. Key differences from the source:

  • ObjectId → BIGINT UNSIGNED AUTO_INCREMENT primary keys (or CHAR(26) ULIDs for sortable public-safe ids — recommended for order/deposit ids shown in URLs)
  • Money Float microcents → BIGINT cents (simpler, exact integer math)
  • String[] arrays → child tables or JSON columns where opaque/admin-only
  • Json fields → native MySQL JSON columns
  • Enums → MySQL ENUM(...) columns
  • Relations → FK constraints with ON DELETE rules matching current semantics

6.Proposed folder structure

No framework, no autoloader magic beyond a tiny PSR-4-lite loader.

/php-edition
  /config
    config.example.php        # DB creds, secrets, payment keys — copied to config.php by installer
  /install
    install.php                # web installer wizard (schema import + first admin + config write)
    schema.sql
  /public                       # web root — only this directory is exposed by the host
    index.php                   # front controller / router
    /assets (css, js, images)
    /uploads                    # avatars, proofs, attachments (writable)
  /src
    /Core        (Router, DB (PDO singleton), Session, Csrf, Request, Response, View)
    /Auth        (Login, Register, OTP, TOTP, Google OAuth, Ban check middleware)
    /Models      (one class per table, thin data-mapper, prepared statements only)
    /Services    (Wallet, Checkout, Deposits, GiftCodes, Promo, FlashSale, Referral,
                  SpecialPrice, SupportBot, SupplierApi, PlatformApi, Settlement)
    /Controllers (Storefront, Account, Wallet, Checkout, Admin\*, Api\V1\*, Webhooks\*)
    /Views       (plain PHP templates, layout.php + partials, Tailwind classes)
    /Cron        (deposits_poll.php, settlement_daily.php, activity_log_purge.php)
  /docs
    PRD.md (this file), API.md (Platform API reference), INSTALL.md

Routing: a single public/index.php front controller with a small hand-rolled router (regex route table → controller method), avoiding any Composer dependency.

8.Open questions confirm before Phase 0

  1. IDs: auto-increment ints (simplest, fastest) vs ULIDs (nicer for public URLs, avoids enumeration). Recommend ULIDs for orders, deposits, gift_codes; plain ints elsewhere.
  2. Multi-currency: current system is USD-only by design. Keep that constraint for v1?
  3. Licensing/anti-piracy for the resale product itself: bake a license-key check into the PHP app (since this codebase is being sold to others), or is that a separate concern outside this PRD?
  4. Branding: should the installer include a "rebrand wizard" (site name/logo/colors) so each buyer can white-label without touching code?
  5. Payment gateways: confirm which of Cashfree/Binance Pay/manual UPI/QRIS/eSewa are must-have for v1 vs admin-toggleable per deployment.

9.Summary

Everything in the current Next.js DripClient — storefront, wallet, checkout, reseller tiers, admin console, support bot, Platform API, supplier auto-fulfillment — is in scope for the PHP edition, built in 6 phases on plain PHP 8 + MySQL with zero Composer/npm/build-step dependencies, installable via a web wizard like a classic PHP script product. Phase 1 alone is enough to be sellable; full parity lands at Phase 5.
